# Retro: Phase 2 End — Dashboard Scaffold + Supabase Cloud Go-Live

## Went well
1. **Vendor-blind architecture delivered end-to-end.** 17 repositories extending BaseRepository with `requireTenant(ctx)` guard + 4 domain services (GST / FEFO / StockMovement / LedgerImpact) + IAuthAdapter / IStorageAdapter adapters. No `@supabase` SDK import anywhere outside `src/adapters/**`. This paid off during the Supavisor P1001 throttle incident — switching to SQL Editor paste bypass did not require touching any business logic; only the schema/seed transport changed.
2. **Incident handling of the auto-push mishap (forensic → 2 explicit rollbacks)** was fast and surgical. We proved zero credential leaks (full history 5-pattern grep → 0 matches) before touching any reflogs, then executed 2 successive git soft-reset + `push --force-with-lease origin main` steps exactly matching the user's escalating explicit orders (1 commit back → then to SHA `9fdb352` Initial commit). No work was lost (all edits remained on disk as uncommitted changes), ahead/behind divergence returned to 0 both times.
3. **The drift probe methodology (04-drift-probe-and-fix.sql Part 1 silent fix + Part 2 8-row grid)** — a direct result of the user correctly ordering full verify BEFORE seed retries after the 42601 ON CONFLICT parser failure — exposed that CREATE TABLE-only schema context exports omit 5 critical dimensions (enum labels, unique indexes, RLS flags, GRANTs, row counts) that the seed paste silently depends on. Without this the 2nd seed retry would have been ambiguous; with it the state was 100% visible before retrying. This pattern should become the standard pre-seed verification step on every new Supabase project going forward.
4. **Deterministic idempotent SQL files.** After burning ~25 minutes on 3 successive ON CONFLICT / CTE parser edge case rewrites (42601 stacking ON CONFLICT clauses → CTE outer WHERE NOT EXISTS cannot see VALUES columns → etc.), the final 8× DO block insert-only form survived re-pasting without a single duplicate row. Idempotency was a hard requirement, and we achieved it by the last iteration.

## Went poorly
1. **Tripped Supavisor rate-limit with diagnostic probes.** 30 successive prisma validate/push/seed + raw TCP probes in a tight 30-minute diagnostic loop triggered the free-tier authenticated pg-wire new-session rate limiter. P1001 is an opaque error (no libpq bytes, no Postgres greeting) that makes root cause invisible unless you do differential raw TCP / lightweight validate / full session side-by-side testing. We lost ~45 minutes isolating this and then writing the SQL Editor paste workaround. We recovered but at the cost of time.
2. **PowerShell 5.1 incompatibilities re-appeared twice.** First was the `--compiler-options` embedded JSON quote stripping → SyntaxError on db:seed script; workaround via `tsconfig.seed.json` external file took ~5 min. Second was PS5.1 not supporting ternary operators (`a ? b : c`) when we tried writing a combined seed+verify one-liner script. Rule should have been "always write PowerShell 5.1 compatible scripts" we learned it the hard way by trying PS7 syntax.
3. **Deprecated direct-host assumption delayed URI alignment 10 min.** Early on we assumed DIRECT_URL must use legacy `db.*.supabase.co:5432` — this is the format in most older (pre-Supavisor) documentation. Modern projects provisioned post-early-2025 use the pooled Supavisor hostname for BOTH ports. Only after user literally pasted their Dashboard Connection strings screenshot showing same host for both did we align correctly.
4. **Config drift for SUPABASE_STORAGE_BUCKET was allowed to persist unnoticed because we skipped Storage setup.** We touched only the public Postgres schema during Phase 2 cloud go-live; Storage buckets / dashboard primitives are entirely separate and the `.env.local → .env.example` mismatch was caught only because post-generation rule #85 (mandatory env compare) flagged it. Would have cost a lot of time later at Phase 3b first upload.

## Changes for next time
1. **Connection probe rate limit guardrails.** Write a project rule (Do Not section candidate) that diagnostic Prisma/Postgres probes against any Supabase pooler may not exceed: ≤ 2 validate + ≤ 1 push + ≤ 1 seed attempts in any 10-minute window. If a probe fails, pause and write a SQL Editor paste-based alternative before retrying. Pre-emptive throttle avoidance is faster than differential diagnosis of opaque P1001s.
2. **Prefer SQL-only first provisioning workflow for all new Supabase projects.** Because Supabase already ships an HTTPS SQL Editor and the GoTrue/REST connectivity is proven via SDK before any pg-wire contact, default to: (a) verify REST/Auth, (b) prisma migrate diff → offline SQL, (c) 01→04→02→03 paste sequence, (d) only THEN try Prisma Client over pg-wire as validation step — not as first pass.
3. **Always write external tsconfig files for ts-node.** Never use `--compiler-options '{json}'` inline in package.json on Windows. Any new seed/utility ts-node scripts follow the same `tsconfig.<script>.json` pattern with explicit module overrides + transpileOnly.
4. **Mandatory env diff check BEFORE every close-out check-list sign-off.** Not just at daily triage time. After every scaffold that edits `.env.example` or `.env.local`, grep the two side-by-side and print the variable set diff.
5. **Phase 3 retrospective to also include RLS policies + storage bucket existence checks.** Close-out checklist for Phase 3 Core Masters CRUD must explicitly include: all 19 RLS tenant-scoped policies written + verified against real JWT, Storage bucket name matches BOTH env files and EXISTS in dashboard with authenticated policy.
